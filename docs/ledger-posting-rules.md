# กฎลงบัญชี — สิ่งที่ต้องตกลงกับทีม Ledger Bridge

> เอกสารนี้เขียนไว้ให้ **ส่งให้ทีม Ledger Bridge และนักบัญชีอ่านก่อนนัดคุย**
> จะได้ไม่ต้องเสียเวลานัดรอบแรกไปกับการอธิบายว่าเราส่งอะไรมา
>
> ฝั่ง Sentiara พร้อมส่งแล้ว · ตัวอย่าง payload ในเอกสารนี้ **ดึงจากระบบจริง**
> ไม่ได้เขียนขึ้นใหม่ให้ดูดี

---

## 1 · ตอนนี้ติดอะไร

Sentiara ส่ง **เหตุการณ์** เข้าคิวของ Ledger Bridge ได้แล้ว และส่งได้จริง —
แต่เหตุการณ์ทั้งหมดไปค้างอยู่ที่หน้า **"งานค้างจาก PMS"** เพราะยังไม่มีกฎลงบัญชี
ที่เซ็นรับ · **นี่คือพฤติกรรมที่ถูกต้อง ไม่ใช่ความผิดพลาด** — ระบบกันไม่ให้ใคร
สร้างกฎแล้วเอาไปลงบัญชีเองโดยไม่มีนักบัญชีตรวจ

ผลคือ **ยังใช้กับบัญชีจริงไม่ได้เลย** จนกว่าจะตั้งกฎเสร็จ

### เส้นแบ่งความรับผิดชอบ

```
Sentiara ──เหตุการณ์──▶ คิวรับข้อมูล ──กฎลงบัญชี──▶ ใบสำคัญ ──▶ งบการเงิน
   เราจบตรงนี้                          ↑
                            ทีม Ledger Bridge + นักบัญชี ทำตรงนี้
```

Sentiara **ไม่ส่งเดบิต/เครดิต** และไม่ควรส่ง เพราะผังบัญชีของแต่ละโรงแรม
ไม่เหมือนกันและเปลี่ยนได้โดยที่ PMS ไม่ต้องรับรู้ (ตามที่เอกสารผู้ขายระบุไว้เอง)

## 2 · ใครต้องทำอะไร

| # | ต้องมี | ตั้งที่ไหน | ใครทำ | ตอนนี้ |
|---|---|---|---|---|
| 1 | ชนิดเอกสาร (`docType`) 5 ชนิด พร้อมรูปแบบเลขที่ | ทะเบียน | นักบัญชี | ❌ |
| 2 | **กฎลงบัญชีของแต่ละชนิด ที่เซ็นรับแล้ว** | ทะเบียน | นักบัญชี | ❌ |
| 3 | ผังบัญชีและการผูกช่องบัญชี | ผังบัญชี | นักบัญชี | ❌ |
| 4 | อัตราภาษีที่รับรองแล้ว (VAT 7% · หัก ณ ที่จ่าย) | ภาษี | นักบัญชี | ❌ |
| 5 | กุญแจเครื่องจักรของเครื่องลูกค้าจริง | ทะเบียน | ทีม LB | ❌ ชุดที่มีเป็นชุดทดสอบ |

## 3 · เหตุการณ์ 5 ชนิดที่เราส่ง

ทุกเหตุการณ์ห่อเหมือนกันหมด — จำนวนเงินเป็น **สตริงเสมอ** และวันที่เป็น
**วันทำการ** ไม่ใช่เวลาเครื่อง

```json
{ "seq": 101, "eventType": "NA", "businessDate": "2026-09-13",
  "payload": { "eventId": "...", "docType": "NA", "businessDate": "...", ... } }
```

### NA · ปิดยอดรายคืน

เกิดตอนปิดยอดรายคืน (ตี 2) · **หนึ่งใบต่อหนึ่งการเข้าพักต่อหนึ่งคืน**

```json
{
  "seq": 101, "eventType": "NA", "businessDate": "2026-09-13",
  "payload": {
    "eventId": "NA-2026-09-13-BK-FE705B5F", "docType": "NA",
    "businessDate": "2026-09-13", "bookingRef": "BK-FE705B5F",
    "room": "108", "guestName": "คุณอนันต์ ศรีสุข", "source": "direct",
    "lines": [
      { "category": "ROOM",     "grossAmount": "1650.00", "netAmount": "1542.06" },
      { "category": "FNB",      "grossAmount": "130.00",  "netAmount": "121.50"  },
      { "category": "SERVICE",  "grossAmount": "120.00",  "netAmount": "112.15"  },
      { "category": "DISCOUNT", "grossAmount": "200.00",  "netAmount": "186.92"  }
    ],
    "vatBase": "1588.79", "vatAmount": "111.21", "vatPct": 7,
    "grandTotal": "1700.00"
  }
}
```

`category`: `ROOM` · `FNB` · `MINIBAR` · `LAUNDRY` · `SERVICE` · `DISCOUNT`

> **ยอดทุกบรรทัดเป็นบวกเสมอ — `DISCOUNT` ก็เป็นบวก**
> ทิศทางบอกด้วย `category` ไม่ใช่ด้วยเครื่องหมาย ซึ่งตรงกับผังบัญชีที่กำหนดให้
> `4190-00 ส่วนลดจ่าย` มีด้านปกติเป็นเดบิตอยู่แล้ว
>
> เดิมเราส่ง `-186.92` แล้วกฎที่มีเงื่อนไข `> 0` กรองทิ้ง**เงียบ ๆ** ใบไม่สมดุล
> เท่าส่วนลดพอดี · **แก้ที่ฝั่ง Sentiara แล้ว** (มีเทสคุมไว้ 3 ข้อ)

**กระทบยอด:** รายได้ที่ไม่ใช่ส่วนลด − ส่วนลด = `vatBase` · แล้ว `+ vatAmount` = `grandTotal`
`1542.06 + 121.50 + 112.15 − 186.92 = 1588.79` · `+ 111.21 = 1700.00` ✓

| | บัญชี | จำนวน |
|---|---|---|
| เดบิต | `1130-01` ลูกหนี้การค้า | `grandTotal` |
| เดบิต | `4190-00` ส่วนลดจ่าย | บรรทัด `DISCOUNT` |
| เครดิต | `4100-01/02/09` รายได้ แมปจาก `category` | `netAmount` รายบรรทัด |
| เครดิต | **`2136-00` ภาษีขายยังไม่ถึงกำหนด** (ดูข้อ 4.1) | `vatAmount` |

### DEP · รับเงินมัดจำ

> **เกิดเฉพาะเมื่อ `method == "deposit"` เท่านั้น** · การรับเงินด้วยวิธีอื่น
> (`cash` `transfer` `card` `promptpay`) ออกมาเป็น `STL` ไม่ใช่ `DEP`
>
> แยกที่ `method` ไม่ใช่ที่สถานะการจอง เพราะสถานะเปลี่ยนได้ตลอดเวลา
> แต่ `eventId` ต้องคงที่ตลอดกาล

```json
{
  "eventId": "DEP-PY-8AD8047C", "docType": "DEP",
  "businessDate": "2026-09-13", "bookingRef": "BK-FE705B5F",
  "room": "108", "guestName": "คุณอนันต์ ศรีสุข",
  "method": "deposit", "amount": "1000.00",
  "vatBase": "934.58", "vatAmount": "65.42", "vatPct": 7,
  "settlement": [ { "method": "deposit", "amount": "1000.00" } ]
}
```

| | บัญชี | จำนวน |
|---|---|---|
| เดบิต | `1111-00` / `1112-01` ตาม `method` | `amount` |
| เครดิต | `2130-01` เงินมัดจำรับล่วงหน้า | `amount` |
| — | VAT: **ขึ้นกับข้อ 4.2** อย่าเพิ่งตั้ง (ดูคำเตือนท้ายข้อ 4.1) | |

### STL · รับชำระ / ปิดบิล

ออกมาสองจังหวะและใช้ `docType` เดียวกัน แยกด้วยฟิลด์ `closing`

**ก) รับชำระระหว่างพัก** — `closing` ไม่มี

```json
{
  "eventId": "STL-PY-8AD8047C", "docType": "STL",
  "businessDate": "2026-09-13", "bookingRef": "BK-FE705B5F",
  "room": "108", "guestName": "คุณอนันต์ ศรีสุข",
  "method": "transfer", "amount": "1000.00",
  "vatBase": "934.58", "vatAmount": "65.42", "vatPct": 7,
  "settlement": [ { "method": "transfer", "amount": "1000.00" } ]
}
```

**ข) ปิดบิล** — `"closing": true` และมีเลขที่ใบกำกับภาษี

```json
{
  "eventId": "STL-CLOSE-BK-FE705B5F", "docType": "STL",
  "businessDate": "2026-09-13", "bookingRef": "BK-FE705B5F",
  "room": "108", "guestName": "คุณอนันต์ ศรีสุข", "source": "direct",
  "closing": true,
  "grandTotal": "3350.00", "paidTotal": "3350.00", "balanceDue": "0.00",
  "vatBase": "3130.84", "vatAmount": "219.16", "vatPct": 7,
  "taxInvoiceNo": "INV-2569-00002"
}
```

| | บัญชี | จำนวน |
|---|---|---|
| (ก) เดบิต | `1111-00` / `1112-01` ตาม `method` | `amount` |
| (ก) เครดิต | `1130-01` ลูกหนี้การค้า | `amount` |
| (ก) เดบิต | `2136-00` ภาษีขายยังไม่ถึงกำหนด | `vatAmount` |
| (ก) เครดิต | `2135-00` ภาษีขาย | `vatAmount` |
| (ข) | ปิดใบ ออกเลขที่ใบกำกับ · `balanceDue > 0` = ยังค้าง คงยอด `1130-01` ไว้ | |

### EXP · รายจ่าย

```json
{
  "eventId": "EXP-EX-06C4D7BA", "docType": "EXP",
  "businessDate": "2026-09-13",
  "category": "maintenance", "label": "จ้างซักผ้าปูที่นอน",
  "amount": "9800.00", "paid": true, "dueDate": null,
  "withholdingKind": "service", "withholdingTax": "294.00",
  "netPayable": "9506.00"
}
```

`category` 11 หมวด: `payroll` `electricity` `water` `telecom` `supplies` `ota`
`maintenance` `marketing` `bankfee` `interest` `other`
`withholdingKind`: `none` `service` `rent` `professional` `advertising` `transport`

| | บัญชี | จำนวน |
|---|---|---|
| เดบิต | บัญชีค่าใช้จ่ายตาม `category` | `amount` |
| เครดิต | `2132-03` / `2132-53` ภาษีหัก ณ ที่จ่ายค้างนำส่ง (ดูข้อ 4.3) | `withholdingTax` |
| เครดิต | เจ้าหนี้ / เงินสด ตาม `paid` | `netPayable` |

> `amount = withholdingTax + netPayable` เสมอ — มีเทสคุมทุกอัตราและทุกยอด

### ADJ · ใบลดหนี้ (ม.86/10)

```json
{
  "eventId": "ADJ-creditnote-CN-2569-00001", "docType": "ADJ",
  "businessDate": "2026-09-13",
  "reason": "creditnote", "sourceRef": "CN-2569-00001",
  "amount": "500.00", "vatAmount": "32.71",
  "creditNoteNo": "CN-2569-00001",
  "memo": "ลดหนี้ใบกำกับ INV-2569-00002 · BK-FE705B5F · คืนค่าอาหารที่เสิร์ฟผิด"
}
```

`amount` คือยอดรวมที่ลด (มี VAT อยู่ข้างใน) · `vatAmount` คือส่วน VAT ของยอดนั้น
**ไม่มีเลขที่ใบลดหนี้ ระบบฝั่งเราปฏิเสธตั้งแต่ต้นทาง** ไม่ปล่อยออกมา

| | บัญชี | จำนวน |
|---|---|---|
| เดบิต | รายได้ที่ลด (หรือบัญชีรับคืน) | `amount − vatAmount` |
| เดบิต | `2135-00` ภาษีขาย | `vatAmount` |
| เครดิต | `1130-01` ลูกหนี้ หรือเงินสดที่คืนไป | `amount` |

## 4 · ห้าเรื่องที่นักบัญชีต้องชี้ขาด

เราเสนอทางไว้แล้วพร้อมเหตุผล แต่**ตัดสินใจแทนไม่ได้**

### 4.1 VAT ของ NA เข้าบัญชีไหน — และ **ห้ามนับสองรอบ**

ผังปลายทางมีทั้ง `2135-00 ภาษีขาย` และ `2136-00 ภาษีขายยังไม่ถึงกำหนด`
**ม.78/1(1) ประมวลรัษฎากร** — ความรับผิดในการเสีย VAT ของค่าบริการเกิดเมื่อ
**ได้รับชำระเงิน** ไม่ใช่เมื่อให้บริการ

→ เราเสนอ `2136-00` ตอน NA แล้ว**โอน**เป็น `2135-00` ตอนรับเงิน

> ### ⚠ จุดที่พลาดแล้วภาษีขายบวมสองเท่า
>
> `NA` มี `vatAmount` และ `STL`/`DEP` ก็มี `vatAmount` มาด้วย
> **ถ้ากฎสองตัวต่างคนต่างเครดิต `2135-00` ภาษีขายจะถูกนับสองรอบ**
>
> กฎฝั่งรับเงินต้อง **โอน** ไม่ใช่ **ตั้งใหม่**
> ```
> เดบิต  2136-00  ภาษีขายยังไม่ถึงกำหนด    vatAmount
> เครดิต 2135-00  ภาษีขาย                  vatAmount
> ```
> ไม่ใช่ `เครดิต 2135-00` คู่กับรายได้ — รายได้รับรู้ไปแล้วตอน `NA`

**สองกรณีที่กฎต้องรับมือ และเราตอบแทนนักบัญชีไม่ได้**

1. **รับเงินก่อนเข้าพัก (มัดจำล่วงหน้า)** — ยังไม่มี `NA` ใบไหนเกิดขึ้น
   `2136-00` จึงยังไม่มียอดให้โอน · ถ้ากฎเดบิต `2136-00` ตรง ๆ จะได้ยอดติดลบ
   ค้างไว้จนกว่า `NA` คืนแรกจะมา
   → ขึ้นกับคำตอบข้อ 4.2 ว่ามัดจำมี VAT หรือไม่ **ตอบข้อ 4.2 ก่อนถึงเขียนกฎ DEP ได้**

2. **จ่ายบางส่วน** — `STL` แต่ละครั้งมี `vatAmount` ของยอดที่รับครั้งนั้น
   ไม่ใช่ของทั้งบิล · โอนทีละครั้งแล้วรวมกันจะเท่ากับ VAT ทั้งใบพอดี
   (ยกเว้นเศษสตางค์จากการปัดทีละครั้ง — เราปัดที่ต้นทางแล้วยกส่วนต่างให้ภาษี
   ตัวเลขจึงตรงกับที่แขกจ่ายเสมอ แต่**ผลรวมของหลายครั้งอาจต่างจากยอดทั้งใบ
   ไม่กี่สตางค์** ถ้ารับกติกานี้ไม่ได้ ให้ใช้ `vatAmount` จากใบ `closing: true`
   เป็นตัวตั้งแล้วกลับรายการที่โอนไว้ก่อนหน้า)

### 4.2 มัดจำมี VAT หรือไม่
ชื่อบัญชี `2130-01 เงินมัดจำรับล่วงหน้า` บ่งว่าถือเป็น **ค่าบริการล่วงหน้า**
→ มี VAT และต้องออกใบกำกับตั้งแต่วันรับมัดจำ
ถ้าถือเป็น **เงินประกันที่คืนได้** → ไม่มี VAT
**คนละกฎกันทั้งชุด ต้องเลือกก่อนตั้งกฎ**

### 4.3 ภาษีหัก ณ ที่จ่าย ใช้บัญชีไหน
`2132-03` (ภ.ง.ด.3 — บุคคลธรรมดา) กับ `2132-53` (ภ.ง.ด.53 — นิติบุคคล)
ตอนนี้ Sentiara ส่ง `withholdingKind` มาแต่**ยังไม่มีฟิลด์ประเภทผู้รับเงิน**
→ ถ้าต้องแยกสองบัญชี **เราต้องเพิ่มฟิลด์นี้** บอกมาแล้วเราทำให้

### 4.4 ส่วนลดลงบัญชีอย่างไร
`DISCOUNT` ส่งมาเป็นยอดติดลบในบรรทัด `lines`
→ หักออกจากรายได้ หรือลงเป็นบัญชีส่วนลดจ่ายแยก

### 4.5 ค่าคอมมิชชัน OTA
ตอนนี้จองผ่าน OTA **ยังไม่สร้างรายจ่ายค่าคอมอัตโนมัติ**
→ ถ้าต้องการ บอกมาว่าให้ลงหมวดไหน แล้วเราทำให้ (มีหมวด `ota` รออยู่แล้ว)

### 4.6 ชื่อ docType ไม่ตรงกัน และฟิลด์ที่กฎเรียกแต่เราไม่ส่ง

เอาเอกสารนี้ไปยิงผ่านเครื่องยนต์กฎจริงแล้วเจอสามจุด · **ข้อ 3 แก้ที่ฝั่งเราแล้ว**
อีกสองข้อต้องตัดสินว่าใครขยับ

| กฎที่มีอยู่ (`hotel.ts`) | เราส่ง | ต้องทำ |
|---|---|---|
| `NA` ปิดยอดรายคืน | `NA` | ✅ ตรงแล้ว |
| `DP` รับเงินมัดจำ | `DEP` | เลือกชื่อเดียว |
| `FS` เช็คเอาต์ รับชำระ | `STL` | เลือกชื่อเดียว |
| `OC` ค่าคอมมิชชั่น OTA | — | ดูข้อ 4.5 |
| — | `EXP` | **ยังไม่มีกฎ** |
| — | `ADJ` | **ยังไม่มีกฎ** — จำเป็นก่อนใช้จริง (ม.86/10) |

**ฟิลด์ที่กฎเรียกแต่เราไม่ได้ส่ง**

- `doc.serviceCharge` — เราส่งค่าบริการเป็น**บรรทัด** `category: "SERVICE"`
  ไม่ใช่ฟิลด์ระดับเอกสาร · `revenue_center` ก็ยังไม่มีคีย์ `SERVICE`
  → เสนอให้**เพิ่ม `SERVICE` → `4100-09` ในตารางแมป** แล้วตัดกิ่ง `doc.serviceCharge`
  ทิ้ง จะได้เป็นทางเดียวกับ FNB/ROOM ไม่ต้องมีสองกลไกสำหรับเรื่องเดียวกัน
- `doc.commission` — ยังไม่มีฝั่งเรา ผูกกับข้อ 4.5

**ถ้าจะให้ Sentiara เปลี่ยนชื่อ `docType` บอกได้ แก้ที่เดียวจบ** — แต่ต้องรู้ก่อน
ส่งของจริง เพราะ `eventId` มีชื่อชนิดอยู่ข้างใน และ **`eventId` ต้องคงที่ตลอดกาล**
เปลี่ยนทีหลังแปลว่าเหตุการณ์เดิมจะถูกมองเป็นเหตุการณ์ใหม่แล้วลงบัญชีซ้ำ

## 6 · วิธียืนยันว่าตั้งเสร็จแล้วใช้ได้จริง

หลังตั้งกฎเสร็จ ให้รันตามลำดับนี้ — **อย่าเชื่อว่าเสร็จเพราะไม่มี error**

```bash
cd server
python -c "from pms.ledger import collect; ..."   # กวาดเหตุการณ์เข้าคิว
python scripts/night_audit.py                     # หรือปิดยอดรายคืนจริง
```
แล้วเปิดจอเจ้าของ → แท็บ **บัญชีคู่ & ส่งเข้าโปรแกรมบัญชี** → กดส่ง

**ต้องดูตัวเลข `inserted` จากคำตอบ ไม่ใช่แค่ว่าได้ HTTP 200/202**

> ⚠ **กับดักที่เคยทำข้อมูลหายเงียบ ๆ มาแล้ว**
> ปลายทางมี watermark · `seq` ที่ต่ำกว่าค่านั้นถูกรายงานว่าเป็น `duplicates`
> เราเคยส่งไป 4 รายการ ได้ `202` ไม่มี error แต่**ไม่มีอะไรเข้าคิวเลย**
> ต้นเหตุคือสคริปต์ตรวจของผู้ขายเองใช้ `Date.now()` เป็น `seq` ซึ่งดัน
> watermark ไปเก้าร้อยกว่าล้านตั้งแต่รันตรวจครั้งแรก
>
> ฝั่งเราแก้แล้วสองชั้น (`align_sequence()` + นับ `inserted` จริง) แต่
> **ควรบอกทีมเขาด้วย** เพราะสคริปต์ตรวจของเขายังทำแบบนั้นอยู่

ถือว่าผ่านเมื่อ: ส่ง 1 เหตุการณ์ → ขึ้นเป็นใบสำคัญที่ **เดบิตเท่ากับเครดิต** →
ส่งซ้ำรายการเดิม → **ยอดไม่ขยับ**
