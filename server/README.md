# Sentiara PMS — หลังบ้านตัวจริง

หลังบ้านของระบบจัดการโรงแรม เขียนด้วย FastAPI + SQLAlchemy + SQLite
รับหน้าที่ตั้งแต่จองห้อง ลงบิล ออกใบกำกับภาษี ไปจนถึงส่งรายการเข้าโปรแกรมบัญชี

หน้าจอเดโมที่อยู่ระดับบน (`prototype/src/`) ยังเก็บข้อมูลใน localStorage อยู่
ตัวนี้คือของจริงที่ตั้งใจให้ frontend ย้ายมาต่อ **ทีละจอ** ไม่ต้องรื้อพร้อมกันทั้งหมด

---

## เริ่มใช้

```bash
cd server
pip install -r requirements.txt
python -m pms.seed                      # ผังห้อง 43 ห้อง + ตัวอย่างที่กดต่อได้ทันที
uvicorn pms.app:app --reload --port 8900
```

เปิด <http://localhost:8900/docs> จะเห็นทุกเส้นทางพร้อมลองยิงได้จากหน้าเว็บ

```bash
python -m pytest -q                     # 176 เทส
```

ข้อมูลตั้งต้นจงใจสร้างการเข้าพักที่ **จบครบวงจรแล้วหนึ่งราย** — ปิดบิลและออก
ใบกำกับภาษีเรียบร้อย — เพื่อให้มีของจริงรอส่งเข้าระบบบัญชีตั้งแต่นาทีแรก
ไม่ต้องนั่งกดสร้างเองก่อนถึงจะทดสอบการเชื่อมต่อได้

## สามเรื่องที่ออกแบบไว้กันพังโดยเฉพาะ

### 1. จองซ้ำห้องเดียวกันเป็นไปไม่ได้ — เพราะฐานข้อมูลห้าม ไม่ใช่เพราะโค้ดเช็ก

`room_night` มี `UNIQUE(room_id, night)` และ `create_booking()` **ไม่เช็กว่าห้องว่างก่อน**
แต่ยิง `INSERT` แล้วปล่อยให้คีย์ไม่ซ้ำเป็นคนปฏิเสธ

วิธี "เช็กก่อนแล้วค่อยบันทึก" มีช่องว่างระหว่างสองจังหวะเสมอ ถ้าสองคำขอเข้ามาพร้อมกัน
ทั้งคู่จะเห็นว่าว่างแล้วจองทั้งคู่ — แขกสองรายได้ห้องเดียวกัน การตัดสินจึงต้องอยู่ใน
ฐานข้อมูล ไม่ใช่ในโค้ดที่ถูกแทรกกลางคันได้

`availability()` มีไว้ให้หน้าจอแสดงผลเท่านั้น **ห้ามเอาผลของมันมาตัดสินใจแทนการจอง**

### 2. เงินเป็นสตางค์จำนวนเต็มทั้งระบบ ไม่มี float แม้แต่ที่เดียว

`0.1 + 0.2 != 0.3` ในเลขทศนิยม ความคลาดเคลื่อนสะสมจนงบไม่ลงตัวและไล่หาย้อนหลังไม่เจอ
ทุกจำนวนเงินเก็บเป็น `int` หน่วยสตางค์ แปลงเป็นบาทเฉพาะตอนแสดงผลกับตอนส่งออก

### 3. VAT ถอดออกจากยอด ไม่ใช่บวกเพิ่ม

ราคาห้องที่ประกาศเป็นราคารวมภาษีแล้ว ตาม ม.86/4 ประมวลรัษฎากร ต้องถอด VAT ออก
ถ้าบวกเพิ่มอีกจะเก็บเงินแขกเกิน `split_vat()` การันตีเสมอว่า `ฐาน + ภาษี == ยอดรวม`

**ตัวเลขภาษีที่ส่งเข้าระบบบัญชียึดจากใบกำกับภาษีเป็นหลัก ไม่คำนวณใหม่** — เอกสารที่ลูกค้าถือ
กับที่ลงบัญชีต้องเป็นตัวเลขชุดเดียวกัน ปัดเศษคนละจังหวะแล้วต่างกันสตางค์เดียว
ฝ่ายบัญชีก็กระทบยอดไม่ลงและหาสาเหตุยากมาก เพราะเอกสารสองใบขัดกันเอง

## เวลา — ไทยเสมอ ห้าม UTC

ทุกที่ที่ต้องรู้เวลาเรียกจาก `pms/clock.py` ที่เดียว **ห้ามเรียก `datetime.now()`
หรือ `datetime.utcnow()` ตรง ๆ ที่อื่น**

ไทยเร็วกว่า UTC เจ็ดชั่วโมง งาน night audit ที่รันตอนตีสองจะได้วันที่เป็น "เมื่อวาน"
ถ้าอ่านเวลาแบบ UTC ทั้งที่ตั้งใจให้เป็นวันนี้ — ยอดขายทั้งคืนไปตกผิดวัน
แล้วงบรายวันสองวันติดกันผิดพร้อมกันทั้งคู่

## ยืนยันตัวตนและสิทธิ์

ทุกเส้นทางใต้ `/api/v1` ต้องแนบโทเคน · `/health` เปิดไว้ให้ตัวเฝ้าระบบเช็กได้

```bash
curl -X POST localhost:8900/api/v1/auth/login   -H 'content-type: application/json'   --data-binary '{"card":"FD-14","pin":"203847"}'
```

ได้โทเคนแล้วแนบไปทุกคำขอ `Authorization: Bearer sts_…`

**บัตรอย่างเดียวไม่พอ ต้องมีรหัสด้วย** — บัตรหล่นในลานจอดรถแล้วคนเก็บได้
เปิดบิลของโรงแรมทั้งใบไม่ได้ · บัตรผิดกับรหัสผิดตอบข้อความเดียวกันและใช้เวลา
เท่ากัน ไม่บอกใบ้ว่าบัตรใบไหนมีอยู่จริง

ฐานข้อมูลเก็บแค่**แฮช** ทั้งรหัสและโทเคน (`hashlib.scrypt` ของไพธอนเอง
ไม่ต้องลงไลบรารีเพิ่ม) ทำหายแล้วออกใหม่อย่างเดียว กู้คืนไม่ได้

| บทบาท | สิทธิ์ |
|---|---|
| `owner` `manager` | ครบทุกข้อ |
| `front` | จอง · บิล · อาหาร · ใบกำกับภาษี · ทะเบียนผู้พัก |
| `pos` | ลงรายการอาหารอย่างเดียว |
| `hk` `tech` | ไม่มีสิทธิ์ทางการเงินเลย |

**พนักงานเคาน์เตอร์ไม่มีสิทธิ์ `approve` และแตะสมุดบัญชีไม่ได้** — คนที่ถูก
ตรวจสอบอนุมัติให้ตัวเองได้เมื่อไร บันทึกการตรวจสอบทั้งหมดก็ไม่มีความหมาย

`audit_event` บันทึกว่าใครทำอะไรเมื่อไร และเก็บ**ชื่อซ้ำไว้ในแถว**ไม่ใช่อ้าง
แค่ id — คนเปลี่ยนชื่อหรือลาออกแล้ว ร่องรอยเก่าต้องยังอ่านออกว่าตอนนั้นใครกด

## ให้หน้าจอต่อเข้ามา

หน้าจอ (`src/`) ทำงานได้**สองโหมดจากบิลด์เดียว** — เดโมคือเครื่องมือขาย
ถ้าทำให้มันต้องมีเซิร์ฟเวอร์ถึงจะเปิดได้ ก็เท่ากับพังเครื่องมือขาย

```bash
npm run dev                                        # โหมดสาธิต · ข้อมูลในเบราว์เซอร์
VITE_API_URL=http://127.0.0.1:8900 npm run dev     # ต่อหลังบ้านตัวจริง
```

ต่อไม่ติดก็ถอยกลับเป็นโหมดสาธิตเงียบ ๆ ไม่มีจอแดง · แถบบนสุดบอกตลอดเวลาว่า
กำลังดูข้อมูลชุดไหนอยู่ เพราะสองอย่างนี้หน้าตาเหมือนกันเป๊ะ

**เซิร์ฟเวอร์เป็นแหล่งความจริง** — หน้าจอยิงหลังบ้านก่อน สำเร็จแล้วค่อยดึงภาพ
ใหม่มาทั้งชุด ไม่วาดไปก่อนแล้วค่อยรู้ว่าถูกปฏิเสธ เพราะครู่นั้นคือครู่ที่
พนักงานเผลอบอกแขกไปแล้วว่าจองได้

ตั้ง `PMS_ORIGINS` เมื่อหน้าจอกับ API อยู่คนละที่อยู่ (ค่าเริ่มต้นเปิดเฉพาะ
`localhost:5173`)

### ส่วนที่ยังไม่ได้ย้ายมา

หลังบ้านยังไม่มีตารางของงานแม่บ้าน สถานะห้อง แชท ใบงานช่าง แต้มลูกค้า และ
หน้าตั้งค่า — ส่วนพวกนี้ยังทำงานในเครื่องต่อไปแม้อยู่โหมดจริง และ**ผังห้อง
ในโหมดจริงยังไม่มีสถานะ "รอแม่บ้าน"** เพราะไม่มีที่มา ห้องที่เพิ่งเช็กเอาต์
จะขึ้นว่าว่างทันที นี่คือของที่ยังขาด ไม่ใช่ของที่ออกแบบมาแบบนี้

## ต่อกับโปรแกรมบัญชี (Ledger Bridge)

**เราส่ง "เหตุการณ์" ไม่ได้ส่ง "รายการบัญชี"** — PMS รู้ว่าคืนนี้ขายห้องได้เท่าไร
แต่ไม่รู้ว่าเงินก้อนนั้นลงบัญชีตัวไหน และไม่ควรรู้ด้วย เพราะผังบัญชีของแต่ละโรงแรม
ไม่เหมือนกันและเปลี่ยนได้โดยที่ PMS ไม่ต้องรับรู้ การแปลงเป็นเดบิต/เครดิตเป็นหน้าที่ของ
**กฎลงบัญชีที่นักบัญชีตั้งและเซ็นรับ** ที่ปลายทาง

> รุ่นก่อนหน้าประกอบใบสำคัญพร้อมเดบิต/เครดิตจากผังบัญชีที่ฝังในโค้ด แล้วยิงไป
> `POST /journal-entries` ซึ่งผิดสัญญาทั้งหลักการ เส้นทาง และรูปแบบข้อมูล
> `pms/ledger.py` เขียนใหม่ทั้งไฟล์แล้ว

```
PMS ──เหตุการณ์──▶ คิวรับข้อมูล ──กฎลงบัญชี──▶ ใบสำคัญ ──▶ งบการเงิน
```

### ห้าชนิดที่ระบบนี้ผลิต

| ชนิด | คือ | ต้นทาง |
|---|---|---|
| `NA` | ปิดยอดรายคืน | `room_night` ของคืนนั้น + รายการที่ลงบิลวันนั้น |
| `DEP` | รับมัดจำ | `Payment` ที่ `method="deposit"` |
| `STL` | รับชำระ / ปิดบิล | `Payment` อื่น ๆ · `close_folio()` |
| `EXP` | รายจ่าย | `Expense` |
| `ADJ` | กลับรายการ | ⚠ ยังไม่มีใครเรียก — รอระบบใบลดหนี้ |

**ค่าห้องรับรู้ทีละคืนจาก `room_night` ไม่ใช่จาก `charge`** — `create_booking()`
ลงค่าห้องทุกคืนเข้าบิลตั้งแต่วันจอง ซึ่งถูกสำหรับบิลแต่ผิดสำหรับบัญชี
จองวันนี้เข้าพักเดือนหน้า รายได้เป็นของเดือนหน้า

### ใช้งาน

```bash
python scripts/night_audit.py                      # ดูอย่างเดียว
LEDGER_DRY_RUN=0 python scripts/night_audit.py     # ส่งจริง
```

```bash
export LEDGER_TOKEN=lbk_...     # กุญแจเครื่องจักร — ห้ามฝังในโค้ดหรือขึ้น git
export LEDGER_SOURCE=sentiara   # ต้องตรงกับ source ของกุญแจ
# LEDGER_URL เว้นว่างไว้ = ไล่หาพอร์ตเองแล้วยืนยันด้วยกุญแจ
```

**อย่าฝังพอร์ต 3111 ไว้ในโค้ด** โปรแกรมเลื่อนพอร์ตเองถ้าไม่ว่าง และเครื่องที่มี
Ledger Bridge ของกิจการอื่นเปิดอยู่ ตัวที่เราต้องการจะไปอยู่พอร์ตถัดไป
ยิงผิดตัวแล้วอาการที่เห็นคือ `401` ซึ่งชวนให้ไปแก้ผิดที่ทั้งวัน

### กันส่งซ้ำ และกับดักที่ต้องรู้

`seq` มาจาก `ledger_outbox.seq` โดยตรง **ไม่ได้สร้างใหม่ตอนส่ง** ส่วน `eventId`
ผูกกับ `ref` ที่สุ่ม (ไม่ใช่ `id` ที่เป็นเลขเรียง — seed ฐานใหม่แล้วเลขวนกลับมาชนกัน)

**`202` แปลว่า "รับไว้แล้ว" ไม่ใช่ "ลงบัญชีแล้ว"** ดูสถานะจริงที่หน้า
"งานค้างจาก PMS" ในโปรแกรมบัญชี

⚠ **กับดัก watermark** — ปลายทางจำไว้ว่ารับถึงลำดับไหนแล้วต่อหนึ่ง `source`
และ **ทิ้งของที่ลำดับต่ำกว่านั้นโดยรายงานว่า `duplicates`** ซึ่งหน้าตาเหมือน
ความสำเร็จทุกประการ ฐานข้อมูลใหม่ของเราเริ่มนับที่ 1 เสมอ ถ้า `source` เดียวกัน
เคยถูกใช้มาก่อน ทุกอย่างที่ส่งจะหายเงียบ ๆ

`align_sequence()` ดันลำดับให้พ้น watermark ก่อนส่งทุกครั้ง และ `send_pending()`
นับ `inserted` จากคำตอบจริง ไม่เชื่อแค่ว่า HTTP สำเร็จ

*(เจอตอนยิงของจริงครั้งแรก — ส่งไป 4 รายการ ได้ `202` ไม่มี error แต่ไม่มีอะไร
เข้าคิวเลย · สคริปต์ `ตรวจก่อนเริ่ม.mjs` ของผู้ขายส่ง `seq` ที่มาจาก `Date.now()`
ซึ่งดัน watermark ไปเก้าร้อยกว่าล้านตั้งแต่รันตรวจครั้งแรก)*

### ยังไม่ได้ทำ ต้องตกลงกับทีมบัญชีก่อน

- **กฎลงบัญชียังไม่ได้ตั้ง** เหตุการณ์ที่ส่งไปค้างที่หน้า "งานค้างจาก PMS"
  รอให้ตั้งกฎก่อน — ถูกต้องแล้ว ไม่ใช่ความผิดพลาด
- **VAT ของ `NA` เข้าบัญชีไหน** ผังบัญชีปลายทางมีทั้ง `2135-00 ภาษีขาย` และ
  `2136-00 ภาษีขายยังไม่ถึงกำหนด` · ตาม ม.78/1(1) ความรับผิดของค่าบริการเกิดเมื่อ
  ได้รับชำระเงิน จึงควรเป็น `2136-00` ตอน `NA` แล้วย้ายเป็น `2135-00` ตอน `STL`
  **นักบัญชีต้องชี้ขาด**
- **มัดจำมี VAT หรือไม่** ชื่อบัญชี `2130-01 เงินมัดจำรับล่วงหน้า` บ่งว่าถือเป็น
  ค่าบริการล่วงหน้า → มี VAT และต้องออกใบกำกับตั้งแต่วันรับมัดจำ
  ถ้าถือเป็นเงินประกันที่คืนได้ก็ไม่มี — **คนละกฎกัน ต้องเลือกก่อน**
- **ภาษีหัก ณ ที่จ่าย 3%** ผังมี `2132-03` (ภ.ง.ด.3) และ `2132-53` (ภ.ง.ด.53)
  รออยู่ ต้องเพิ่มฟิลด์ประเภทผู้รับเงินใน `Expense`
- **ใบลดหนี้** ยังไม่มี — `adjustment_event()` ปฏิเสธการกลับ VAT ที่ไม่มีเลขที่
  ใบลดหนี้ ต้องทำก่อนใช้กับของจริง
- **ค่าคอมมิชชัน OTA** ยังไม่สร้าง `Expense` อัตโนมัติเมื่อ `source="ota"`

## Wi-Fi ที่พัก — ชั้นที่ตอบว่า "session นี้คือใคร"

**ม.26 พ.ร.บ.ว่าด้วยการกระทำความผิดเกี่ยวกับคอมพิวเตอร์ พ.ศ. 2550** ให้ผู้ให้
บริการเก็บข้อมูลจราจรไม่น้อยกว่า 90 วัน โทษปรับไม่เกินห้าแสนบาท · ข้อมูลจราจร
ที่อุปกรณ์เก็บจะไร้ประโยชน์ถ้าโยงกลับไปหาคนไม่ได้ — และนั่นคือชิ้นที่หายไป

| | รู้อะไร | ไม่รู้อะไร |
|---|---|---|
| อุปกรณ์เครือข่าย | MAC นี้ทำอะไร | **MAC นี้คือใคร** |
| ระบบนี้ | คนนี้ชื่ออะไร เลขเอกสารอะไร ห้องไหน | ทำอะไรบนเน็ต |

**ไม่เป็นถังเก็บ log จราจรโดยตั้งใจ** — อุปกรณ์ทำได้ดีกว่าและถูกกว่า ส่วนข้อมูล
ว่าใครเข้าเว็บอะไรเป็นข้อมูลที่ร้อนที่สุดในสายตา PDPA ยิ่งถือน้อยยิ่งดี
เราเก็บแค่ว่า "IP นี้ในช่วงเวลานี้คือแขกคนไหน"

### ต่อกับอุปกรณ์

ไม่ผูกกับยี่ห้อไหน เปิดเป็น HTTP ให้อุปกรณ์เรียกเข้ามา

* **FreeRADIUS** → `rlm_rest` ชี้มาที่ `/wifi/authorize` และ `/wifi/accounting`
  แล้ว Mikrotik / Ruckus / Aruba / Cisco ต่อผ่าน RADIUS ตามปกติ
* **UniFi / Omada** → external captive portal เรียกตรงได้เลย

```bash
export PMS_WIFI_SECRET=...      # ความลับร่วมกับอุปกรณ์ · ส่งมาทาง X-Wifi-Secret
```

**ไม่ตั้งค่า = ปฏิเสธทุกคำขอ ไม่ใช่ปล่อยผ่าน** — ระบบที่ลืมตั้งค่าแล้วเปิดกว้าง
คือระบบที่ไม่มีใครรู้ว่าเปิดกว้างอยู่ · ช่องนี้ต้องอยู่บนวงในเท่านั้น

### รายละเอียดที่มาจากงานหน้างานจริง

* **ออกรหัสตอนเช็กอินเอง** ไม่ต้องมีใครสั่ง — แขกถามหา Wi-Fi เป็นคำถามแรกหลัง
  ได้กุญแจห้อง และรหัสที่ต้องรอพนักงานไปกดคือรหัสที่มักถูกแทนด้วยรหัสรวมของ
  โรงแรม ซึ่งทำให้โยง session กลับไปหาคนไม่ได้เลย
* ชื่อผู้ใช้เป็นเลขห้อง (แขกจำได้) รหัสสุ่ม 6 ตัว **ตัด `0 O 1 l I 5 S` ออก**
  เพราะแขกอ่านจากใบแล้วพิมพ์ผิดเป็นตัวที่หน้าตาเหมือนกัน แล้วโทรมาบอกว่าใช้ไม่ได้
* เก็บแค่แฮชของรหัส — ทำใบหายต้องออกใหม่ ไม่ใช่อ่านของเดิมให้ฟัง
* **หมดอายุหลังเช็กเอาต์ + 3 ชั่วโมง ไม่ใช่ตัดทันที** — แขกที่ยืนรอแท็กซี่อยู่
  ที่ล็อบบี้ยังควรใช้เน็ตได้ ตัดทันทีคือความสะดวกที่หายไปโดยไม่ได้อะไรคืน
* ทำ MAC ให้อยู่รูปเดียวก่อนเทียบ — Mikrotik ส่ง `AA:BB:…` UniFi ส่ง `aabb…`
  ไม่ทำให้เหมือนกัน เครื่องเดิมจะถูกนับใหม่ทุกครั้งแล้วชนเพดานจำนวนเครื่อง
* เครื่องที่ต่ออยู่แล้วต่อกลับได้ตอนชนเพดาน — ไม่งั้นแขกที่เน็ตสะดุดจะกลับ
  เข้ามาไม่ได้ทั้งที่ไม่ได้เพิ่มเครื่อง
* ปริมาณข้อมูลจากอุปกรณ์เป็น**ยอดสะสมของ session** ไม่ใช่ส่วนเพิ่ม บวกเข้าไป
  เรื่อย ๆ เมื่อไร ยอดจะพุ่งเป็นหลายเท่าของจริง
* `prune_sessions()` **ปฏิเสธถ้าตั้งต่ำกว่า 90 วัน** — การตั้งค่าผิดจะทำให้ผิด
  กฎหมายเงียบ ๆ จนกว่าเจ้าหน้าที่จะมาขอแล้วเราไม่มีให้

### ยังไม่ได้ทำ

**ยังไม่ได้ทดสอบกับอุปกรณ์จริง** — เขียนตามสัญญาของ RADIUS และ captive portal
มาตรฐาน แต่ยังไม่ได้ต่อ Mikrotik หรือ UniFi ตัวจริง · และ**ขอบเขตว่าโรงแรม
ขนาดไหนเข้าข่ายผู้ให้บริการอย่างไร ควรให้ทนายยืนยันกับโรงแรมแต่ละราย**
ก่อนเอาไปเป็นคำโฆษณา — ระบบช่วยให้ทำได้ครบ ไม่ได้แปลว่าใช้แล้วถูกกฎหมายแน่นอน

## สำรองและกู้คืน

```bash
python scripts/backup.py                  # สำรองหนึ่งชุด แล้วตรวจให้
python scripts/backup.py --list           # ดูชุดที่มีอยู่
python scripts/backup.py --restore FILE   # กู้คืน (เก็บของเดิมไว้ให้)
python scripts/backup.py --prune 30       # เก็บ 30 ชุดล่าสุด
```

**ไม่ก๊อปไฟล์ `.db` เฉย ๆ** — ฐานเปิดโหมด WAL ข้อมูลที่เขียนล่าสุดอยู่ในไฟล์
`-wal` ยังไม่ลงไฟล์หลัก ก๊อปตอนระบบทำงานอยู่จะได้สำเนาที่**ขาดรายการล่าสุด**
หรือเปิดไม่ขึ้นเลย · ใช้ `sqlite3.Connection.backup()` ที่ทำสำเนาสอดคล้องกัน
ทั้งไฟล์ได้แม้ระบบกำลังรับงาน ไม่ต้องปิดเซิร์ฟเวอร์

ตรวจสำเนาทุกครั้งหลังสำรอง (`PRAGMA integrity_check` + นับแถวจริง) และ
**กู้คืนเก็บของเดิมไว้เป็น `.before-restore-…` เสมอ** เพราะ "กู้คืนผิดไฟล์"
เป็นความผิดพลาดที่เกิดจริงตอนคนกำลังตกใจ

> **ซ้อมกู้คืนอย่างน้อยปีละครั้ง** สำรองที่ไม่เคยลองกู้ ไม่ใช่การสำรอง
> แต่เป็นความรู้สึกปลอดภัย

**ปิดเซิร์ฟเวอร์ก่อนกู้คืนเสมอ** — ไฟล์ที่ยังมีคนเปิดอยู่เขียนทับไม่ได้

## งานที่กฎหมายไทยบังคับ

ไม่เกี่ยวกับเงิน แต่ **ไม่ทำแล้วมีโทษ** และทั้งสองข้อวัดจากเวลา ไม่ใช่จากความตั้งใจ

| แบบ | กฎหมาย | กำหนด |
|---|---|---|
| **ร.ร.3** บัตรทะเบียนผู้พัก | ม.35 พ.ร.บ.โรงแรม 2547 | ผู้พักลงลายมือชื่อทันทีที่เข้าพัก |
| **ร.ร.4** ทะเบียนผู้พัก | ม.35 พ.ร.บ.โรงแรม 2547 | ส่งนายทะเบียนภายใน 24 ชม. · เก็บ ≥ 1 ปี |
| **ตม.30** แจ้งที่พักคนต่างด้าว | ม.38 พ.ร.บ.คนเข้าเมือง 2522 | ภายใน 24 ชม. · ไม่แจ้งมีโทษปรับ |

```
POST /api/v1/bookings/{ref}/guests        ลงทะเบียนผู้พักหนึ่งคน
POST /api/v1/registrations/{id}/sign-rr3  ผู้พักลงลายมือชื่อ
POST /api/v1/registrations/{id}/tm30      บันทึกการแจ้ง ตม.30 พร้อมเลขรับ
POST /api/v1/registry/file-rr4            ส่ง ร.ร.4 ของวันหนึ่ง
GET  /api/v1/registry/due                 ใครยังไม่ครบ เหลือเวลากี่ชั่วโมง
GET  /api/v1/registry/book                เล่มทะเบียนผู้พัก
GET  /api/v1/audit                        ร่องรอยการตรวจสอบ · เขียนอย่างเดียว
```

**สามอย่างที่ตั้งใจทำต่างจากหน้าจอเดโม**

1. **หนึ่งแถวต่อหนึ่งคน ไม่ใช่ต่อหนึ่งการจอง** — กฎหมายลงทะเบียน *ผู้พัก*
   จองใบเดียวมีผู้ใหญ่สองคนต้องมีสองแถว ระบบที่ลงชื่อคนจองแถวเดียวตรวจไม่ผ่าน
2. **เลขประจำตัวบังคับ** — ปล่อยว่างแล้วตามเก็บทีหลัง คือวิธีที่ทำให้ถึงกำหนด
   แล้วยังกรอกไม่ครบ · เลขบัตรประชาชนตรวจ 13 หลัก ต่างชาติใช้เลขหนังสือเดินทาง
3. **`/registry/due` นับถอยหลังให้เห็น** — เก็บข้อมูลครบแต่ไม่มีใครรู้ว่าเหลือเวลา
   เท่าไร สุดท้ายก็เลยกำหนดอยู่ดี

**สิ่งที่ยังทำไม่ได้จริง — อย่าเข้าใจผิดว่าครบแล้ว**

- **ยังไม่ได้ยิงเข้าระบบ ตม.** ต้องมีคนไปกรอกในระบบสำนักงานตรวจคนเข้าเมือง
  แล้วเอาเลขรับกลับมาบันทึก · ระบบบังคับให้ใส่เลขรับ เพราะถ้าไม่บังคับ
  จะขึ้นว่า "แจ้งแล้ว" ได้ทั้งที่ไม่มีใครแจ้ง ซึ่งอันตรายกว่าไม่มีระบบเลย
- **ร.ร.3 เก็บแค่เวลาที่เซ็น ไม่ได้เก็บภาพลายมือชื่อ**
- **`AuditLog.actor` เป็น "system" เสมอ** เพราะยังไม่มีระบบผู้ใช้

## ภาษีหัก ณ ที่จ่าย

```bash
POST /api/v1/expenses   {"...": "...", "wht_kind": "service"}
```

| ประเภท | อัตรา | ใช้กับ |
|---|---|---|
| `none` | — | **ซื้อสินค้า ไม่ต้องหัก** |
| `service` | 3% | ค่าบริการ ค่าจ้างทำของ |
| `professional` | 3% | ค่าวิชาชีพอิสระ |
| `rent` | 5% | ค่าเช่าอสังหาริมทรัพย์ |
| `advertising` | 2% | ค่าโฆษณา |
| `transport` | 1% | ค่าขนส่ง |

สองข้อที่ผิดกันบ่อยจนกลายเป็นค่าปรับ — **หักจากยอดรวม VAT** (ต้องหักจากฐานก่อน VAT)
และ **หักค่าสินค้า** (ใช้กับ *บริการ* เท่านั้น · ซื้อผ้าปูไม่หัก จ้างซักผ้าหัก)

`net + tax == base` เสมอ ตรวจด้วย `assert` — เงินที่ออกจากมือรวมกับที่ค้างนำส่ง
ต้องเท่าค่าใช้จ่ายพอดี ไม่งั้นเจ้าหนี้ทวงส่วนต่างหรือสรรพากรได้ไม่ครบ

เหตุการณ์ `EXP` ส่งครบสามยอด (`amount` · `withholdingTax` · `netPayable`)
ให้กฎลงบัญชีแยกเจ้าหนี้กับภาษีค้างนำส่งได้ · **ยังไม่มีการออก ภ.ง.ด.3/53**
