# Sentiara PMS — หลังบ้านตัวจริง

หลังบ้านของระบบจัดการโรงแรม เขียนด้วย FastAPI + SQLAlchemy + SQLite
รับหน้าที่ตั้งแต่จองห้อง ลงบิล ออกใบกำกับภาษี ไปจนถึงส่งรายการเข้าโปรแกรมบัญชี

หน้าจอเดโมที่อยู่ระดับบน (`prototype/src/`) ยังเก็บข้อมูลใน localStorage อยู่
ตัวนี้คือของจริงที่ตั้งใจให้ frontend ย้ายมาต่อ **ทีละจอ** ไม่ต้องรื้อพร้อมกันทั้งหมด

---

## เริ่มใช้

```bash
cd server
pip install fastapi uvicorn sqlalchemy httpx pytest
python -m pms.seed                      # ผังห้อง 43 ห้อง + ตัวอย่างที่กดต่อได้ทันที
uvicorn pms.app:app --reload --port 8900
```

เปิด <http://localhost:8900/docs> จะเห็นทุกเส้นทางพร้อมลองยิงได้จากหน้าเว็บ

```bash
python -m pytest -q                     # 46 เทส
```

ข้อมูลตั้งต้นจงใจสร้างการเข้าพักที่ **จบครบวงจรแล้วหนึ่งราย** — ปิดบิลและออก
ใบกำกับภาษีเรียบร้อย — เพื่อให้มีของจริงรอส่งเข้าระบบบัญชีตั้งแต่นาทีแรก
ไม่ต้องนั่งกดสร้างเองก่อนถึงจะทดสอบการเชื่อมต่อได้

## สามเรื่องที่ออกแบบไว้กันพังโดยเฉพาะ

### 1. จองซ้ำห้องเดียวกันเป็นไปไม่ได้ — เพราะฐานข้อมูลห้าม ไม่ใช่เพราะโค้ดเช็ก

`room_night` มี `UNIQUE(room_id, night)` และ `create_booking()` **ไม่เช็กว่าห้องว่างก่อน**
แต่ยิง `INSERT` แล้วปล่อยให้คีย์ไม่ซ้ำเป็นคนปฏิเสธ

วิธี "เช็กก่อนแล้วค่อยบันทึก" มีช่องว่างระหว่างสองจังหวะเสมอ ถ้าสองคำขอเข้ามาพร้อมกัน
ทั้งคู่จะเห็นว่าว่างแล้วจองทั้งคู่ — แขกสองรายได้ห้องเดียวกัน การตัดสินจึงต้องอยู่ใน
ฐานข้อมูล ไม่ใช่ในโค้ดที่ถูกแทรกกลางคันได้

`availability()` มีไว้ให้หน้าจอแสดงผลเท่านั้น **ห้ามเอาผลของมันมาตัดสินใจแทนการจอง**

### 2. เงินเป็นสตางค์จำนวนเต็มทั้งระบบ ไม่มี float แม้แต่ที่เดียว

`0.1 + 0.2 != 0.3` ในเลขทศนิยม ความคลาดเคลื่อนสะสมจนงบไม่ลงตัวและไล่หาย้อนหลังไม่เจอ
ทุกจำนวนเงินเก็บเป็น `int` หน่วยสตางค์ แปลงเป็นบาทเฉพาะตอนแสดงผลกับตอนส่งออก

### 3. VAT ถอดออกจากยอด ไม่ใช่บวกเพิ่ม

ราคาห้องที่ประกาศเป็นราคารวมภาษีแล้ว ตาม ม.86/4 ประมวลรัษฎากร ต้องถอด VAT ออก
ถ้าบวกเพิ่มอีกจะเก็บเงินแขกเกิน `split_vat()` การันตีเสมอว่า `ฐาน + ภาษี == ยอดรวม`

**ตัวเลขภาษีในสมุดบัญชียึดจากใบกำกับภาษีเป็นหลัก ไม่คำนวณใหม่** — เอกสารที่ลูกค้าถือ
กับที่ลงบัญชีต้องเป็นตัวเลขชุดเดียวกัน ปัดเศษคนละจังหวะแล้วต่างกันสตางค์เดียว
ฝ่ายบัญชีก็กระทบยอดไม่ลงและหาสาเหตุยากมาก เพราะเอกสารสองใบขัดกันเอง

## เวลา — ไทยเสมอ ห้าม UTC

ทุกที่ที่ต้องรู้เวลาเรียกจาก `pms/clock.py` ที่เดียว **ห้ามเรียก `datetime.now()`
หรือ `datetime.utcnow()` ตรง ๆ ที่อื่น**

ไทยเร็วกว่า UTC เจ็ดชั่วโมง งาน night audit ที่รันตอนตีสองจะได้วันที่เป็น "เมื่อวาน"
ถ้าอ่านเวลาแบบ UTC ทั้งที่ตั้งใจให้เป็นวันนี้ — ยอดขายทั้งคืนไปตกผิดวัน
แล้วงบรายวันสองวันติดกันผิดพร้อมกันทั้งคู่

## เส้นทาง API

ทั้งหมดอยู่ใต้ `/api/v1`

| หมวด | เส้นทาง |
|---|---|
| ห้อง | `GET /rooms` · `GET /availability?check_in=&check_out=` |
| จอง | `POST /bookings` · `GET /bookings/{ref}` · `POST /bookings/{ref}/check-in` · `POST /bookings/{ref}/cancel` |
| บิล | `GET /folios/{ref}` · `POST /folios/{ref}/charges` · `POST /folios/{ref}/payments` · `POST /folios/{ref}/close` |
| ภาษี | `POST /folios/{ref}/tax-invoice` |
| รายจ่าย | `GET /expenses` · `POST /expenses` |
| บัญชี | `GET /ledger/preview/{ref}` · `POST /ledger/send` · `GET /ledger/posts` |

จองซ้ำได้ `409` พร้อมบอกว่า **คืนไหนชน** เพื่อให้คนขายเสนอวันอื่นแทนได้ทันที

## ต่อกับโปรแกรมบัญชี

`POST /api/v1/ledger/send` ส่งทุกอย่างที่ยังไม่เคยส่งสำเร็จ เรียกซ้ำได้ปลอดภัย

**ค่าเริ่มต้นคือ `dry_run` — เตรียมรายการและบันทึกไว้ แต่ไม่ยิงออกจริง**
ใช้ตรวจตัวเลขให้ครบก่อนต่อสายจริง

```bash
export LEDGER_URL=http://localhost:3111    # ที่อยู่ของโปรแกรมบัญชี
export LEDGER_KEY=...                      # กุญแจ (ถ้ามี)
export LEDGER_DRY_RUN=0                    # ยิงออกจริง
```

กันส่งซ้ำสองชั้น: `idem_key` ของทุกรายการมาจาก id ของต้นทาง **ไม่ใช่เวลา** ส่งกี่ครั้ง
คีย์ก็เท่าเดิม และตาราง `ledger_post` มี `UNIQUE` บนคีย์นั้น การส่งซ้ำจึงถูกปฏิเสธ
**ที่ฝั่งเราก่อนออกจากบ้านด้วยซ้ำ** ไม่ฝากความถูกต้องไว้กับปลายทางฝ่ายเดียว
และ HTTP `409` จากปลายทางถือว่าสำเร็จ ไม่ใช่ล้มเหลว

ผังบัญชีตั้งต้นอยู่ใน `ACCOUNTS` ที่หัวไฟล์ `pms/ledger.py` — เปลี่ยนที่เดียวเมื่อได้ผังจริง

### ยังไม่ได้ทำ ต้องตกลงกับทีมบัญชีก่อน

- **รูปแบบข้อความยังไม่ตรงกัน** ตอนนี้ส่งเป็น *ใบสำคัญพร้อมเดบิต/เครดิต* และส่งเงิน
  เป็นสตางค์จำนวนเต็ม ถ้าปลายทางรับเป็น *เหตุการณ์* แล้วไปตั้งกฎลงบัญชีเอง
  และรับเงินเป็นสตริง `"5500.00"` ต้องแก้ชั้นส่งออก (แก้ที่ `to_payload()` ที่เดียว)
- **VAT ของเงินมัดจำ** ม.78/1(1) ความรับผิดของค่าบริการเกิดเมื่อได้รับชำระเงิน
  ถ้าถือมัดจำเป็นค่าบริการล่วงหน้าต้องออกใบกำกับภาษีตั้งแต่วันรับมัดจำ
  ถ้าถือเป็นเงินประกันที่คืนได้ก็ไม่มี VAT — **คนละผังบัญชีกัน ต้องเลือกก่อน**
- **ภาษีหัก ณ ที่จ่าย 3%** รายจ่ายค่าบริการจากนิติบุคคลต้องหัก ตอนนี้ยังไม่รองรับ
- **ใบลดหนี้ / ตั้งรายการกลับ** ใบสำคัญที่ลงแล้วแก้ไม่ได้ ต้องมีเหตุการณ์กลับรายการ

## ยังไม่มีในตัวนี้

พูดกันตรง ๆ — นี่คือ **แกนกลางที่ผลิตตัวเลขบัญชีได้** ไม่ใช่ PMS ที่ครบทุกด้าน

| ยังไม่มี | ทำไมถึงยังไม่ทำ |
|---|---|
| งานแม่บ้าน สถานะห้อง | ไม่กระทบตัวเลขบัญชี |
| เชื่อม OTA / channel manager | ต้องมีสัญญากับ OTA ก่อน |
| POS ร้านอาหาร | ตอนนี้ลงรายการเข้าบิลด้วยมือได้แล้ว |
| หน้าจอเจ้าของกิจการ | หน้าจอเดโมมีแล้ว รอย้ายมาต่อหลังบ้านตัวนี้ |
| กลอนประตู NFC | รอฮาร์ดแวร์จริง |
| ผู้ใช้หลายคน สิทธิ์ตามบทบาท | **ตอนนี้ API ยังไม่มีการยืนยันตัวตนเลย** — ห้ามเปิดออกอินเทอร์เน็ต |
| ทะเบียนผู้พัก ร.ร.3/ร.ร.4 · ตม.30 | ม.35 พ.ร.บ.โรงแรม 2547 บังคับ ต้องทำก่อนใช้จริง |

สองข้อล่างสุดเป็นเรื่องที่ **ต้องเสร็จก่อนเอาไปใช้กับโรงแรมจริง** ไม่ใช่ของแถม
